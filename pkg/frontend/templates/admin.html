Network and retention

These apply as soon as you save. Behind a reverse proxy or load balancer, set the base URL (the public address, which also decides that cookies are Secure) and the trusted proxies (their addresses or ranges, loopback and private also work), so that visitors keep their own address in the audit log and the rate limits.

Analytics and ads

Off while the fields are empty. When you fill one in, visitors who are not signed in are asked, on the sign-in page, the documentation, the status page and the terms and privacy pages, whether they accept it; nothing is loaded before they do, and signed-in people never get it. The privacy policy says so. Ads need a looser content security policy on those pages (inline scripts and images from any HTTPS address), so use them only if you accept that.

HTTPS, HTTP/2 and HTTP/3

{{if .TLS.Active}}HTTPS on{{else}}HTTPS off{{end}}

Plain HTTP stays on the port the server was started with; it speaks HTTP/1.1 and HTTP/2 (also without TLS, for proxies that use it). With a certificate the server also listens for HTTPS on its own port (HTTP/2 and HTTP/1.1), and optionally for HTTP/3 on the UDP port with the same number. A wrong certificate or port cannot lock you out of the plain port. When the web and api parts run as two processes, the web process serves these listeners. Behind a reverse proxy you usually leave this off and let the proxy do TLS.

Sign-in rules

New accounts {{help "registration"}}

{{if .SignupOpen}}Open{{else}}Closed{{end}}

When closed, nobody can create their own account, with a password or through a provider. You can still add people above, and existing accounts keep working.

Two-step verification

{{if eq .Require2FA "everyone"}}Required for everyone{{else if eq .Require2FA "admins"}}Required for administrators{{else}}Optional{{end}}

Users can always turn on a 6-digit code from an authenticator app for signing in with a password. When required, people without one set it up at their next password sign-in. Providers and passkeys are not asked: enforce multi-factor at the provider. Users who have it on, or must, can no longer call the API with their password; they use access tokens.
