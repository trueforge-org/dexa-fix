Getting started

dexa-fix corrects smart-scale results with DEXA scan results. A smart scale is convenient but biased. A DEXA scan is accurate but rare. The app uses the difference between the two on the days you have both, and applies it to the scale readings in between. You get one estimated value per day.

  1. Start the server with dexa-fix serve and open http://localhost:8080.
  2. Create the first account. It becomes the administrator. After that, new accounts are closed until an administrator allows sign-ups (see Signing up).
  3. Enter your height under Settings (needed for BMI, FMI and LMI).
  4. Add one or more DEXA scans.
  5. Add scale readings by hand, by API, or by importing them from Withings. A DEXA scan only calibrates a scale if the scale has a reading on the same day.
  6. Open Estimates to see the daily table, the chart and the calibrations in use.

Stored readings are never changed. Every estimate is calculated from them, so you can change settings at any time and see the result at once.

This page is the same for everyone and needs no sign-in. Small ? badges throughout the app link to the matching section here.

Accounts and sign-in

Each user has an account and sees only their own data. The e-mail address is the account's unique key and what you sign in with. It is compared case-insensitively and stored in lowercase. Names are display names: 1 to 64 characters, and they need not be unique. The first account becomes the administrator. Administrators can make other users administrators; the last administrator cannot be removed.

Password sign-in

  • What: sign in with e-mail address and password on the home page.
  • Format: passwords have 8 characters or more and at most 72 bytes. They are stored as bcrypt hashes.
  • Default: on.
  • Effect of turning it off (Admin page): the sign-in form, the sign-up form and HTTP Basic authentication on the API all stop working. Providers, passkeys and access tokens keep working. The administrator who turns it off must have another way to sign in first (a linked provider or a passkey), so they cannot lock themselves out.
  • Recovery: start the server with --force-password-login (or DEXAFIX_FORCE_PASSWORD_LOGIN=true) to keep password sign-in on whatever the Admin page says, then fix the setting and restart without it.
  • Sessions last 30 days. The cookie is HttpOnly, SameSite=Lax, and Secure when the visitor used HTTPS.

Two-step verification

  • What: a one-time code from an authenticator app, asked for after the password when you sign in with a password. Providers and passkeys do not ask for it, so enforce a second factor at the provider.
  • Turn on: Settings, Two-step verification. Confirm your password, scan the QR code (or type the key in), then enter a code from the app. Standard apps work: 6 digits, a new code every 30 seconds, SHA-1.
  • Recovery codes: ten codes, shown once, in the form xxxx-xxxx-xxxx-xxxx. Each works once, in place of an app code. To get new ones, confirm your password and a code in Settings; the old ones stop working.
  • Turn off: your password and a code, or a recovery code. It cannot be turned off while an administrator requires it.
  • Sign-in: the code is asked for on a second page, and the password check is kept for 5 minutes in a signed cookie (not a session). A code works once. Five wrong codes for an account within 15 minutes block its second step.
  • Administrators: on the Admin page, require it for Nobody (default), Administrators or Everyone. Covered people who have no second step set it up at their next password sign-in.
  • Admin pages: an administrator with two-step verification on is asked for a code again (or a recovery code) before any Admin page. The code entered at sign-in counts. The step-up lasts 15 minutes and is recorded as admin_verified. The JSON API uses access tokens and is not affected.
  • API: HTTP Basic is refused for these accounts. Use an access token.

Password reset

  • Administrator: in the Users list choose Reset link. The one-time link is shown once on the Admin page, is valid for 24 hours and works once. Only a hash is stored. Tick E-mail it to send it instead, when e-mail is set up.
  • Self-service: needs an SMTP server and a base URL on the Admin page, and password sign-in on. The sign-in page then shows Forgot your password?. The user enters their e-mail address, and the answer is the same whether or not the address has an account. A link valid for one hour is mailed in the background, built from the base URL only. Accounts that sign in only through a provider get no e-mail. Limits: 3 e-mails per address and 10 per client address in 15 minutes.
  • Using a link: choose a password of 8 to 72 bytes. With two-step verification on, a code or recovery code is also needed; a reset never bypasses it. The user is signed out everywhere, and all access tokens are revoked. A link stops working when the password or the e-mail address changes.
  • Policy: a user covered by the two-step requirement who has no second step is asked to set one up after the reset.
  • Audit: password_reset_link_created, password_reset_requested, password_reset_email_failed, password_reset_completed and password_reset_invalid.

There are no flags or environment variables for e-mail. Set it on the Admin page.

Passkeys

  • What: a passkey (WebAuthn) signs you in without a password. It is kept on a device or a security key and unlocked with a fingerprint, a face or a PIN. It replaces the password for that sign-in. It is not a second step after a password: the device and its unlock already make two factors, so a passkey sign-in is never asked for a two-step code.
  • Add: Settings, Passkeys, Add a passkey. Give it a name. With a password on the account, confirm your current password. Without one, you need a sign-in from the last 10 minutes.
  • Rename and remove: rename at any time. Removing asks for your password. The last passkey cannot be removed while it is the only way to sign in; add another sign-in method first.
  • Sign in: press Sign in with a passkey on the home page. Browsers that support conditional UI also offer your passkey in the suggestions of the e-mail field. Passkeys are discoverable, so no e-mail address has to be typed.
  • Requirements: browsers offer passkeys only on HTTPS, or on localhost. A passkey belongs to the host name the browser used (the base URL's host, when one is set), and the origin includes the port. If the host name changes, for example to a new domain, existing passkeys stop working and must be added again. With the HTTPS listener, use its HTTPS address. Behind a proxy that terminates TLS, set an https base URL.
  • Other places: a passkey sign-in is recorded with the method passkey, shown in the Users list on the Admin page. A passkey counts as a sign-in method for turning off password sign-in and for unlinking your last provider. A passkey sign-in also counts as the second step for the Admin pages.
  • Your data: the export lists passkey names and dates, never the keys. db copy copies passkeys too.
  • Security: the server stores only the public key and metadata, and a random user handle that says nothing about you. The sign counter must not go backwards; if it does, the sign-in is refused and recorded as passkey_clone_warning. The state of a registration or sign-in is a signed cookie that works once and is valid for 5 minutes. Failed attempts count against the client address limit.
  • Audit: passkey_added, passkey_removed, passkey_login_failed and passkey_clone_warning.
  • Not covered: passkeys are not used as a second factor, and the two-step requirement does not apply to them. They cannot recover an account: a lost device needs another sign-in method or an administrator.

Signing up

The very first account on an empty server can always be created. After that sign-up is closed by default. While it is closed nobody can create their own account, neither with a password nor on first sign-in through a provider. An administrator adds people from the Users list on the Admin page, or opens New accounts on the Admin page (the Open new accounts button). Existing accounts keep working either way.

The sign-up form on the home page only appears when sign-up is open and password sign-in is on.

Sign-in providers

Administrators add external providers on the Admin page. There are three types: OpenID Connect (for example Google), Sign in with Apple, and plain OAuth 2.0. Each provider has a short name, and you register this callback URL with the provider:

https://your-host/auth/<short name>/callback

The Admin page shows the exact callback URL for each provider. It is built from the base URL on the Admin page, or else from the request (see reverse proxy).

  • Linking: users link a provider to their existing account under Settings, Linked accounts.
  • Matching: accounts are matched only by the provider's account id (the subject), never by e-mail address.
  • Create accounts on first sign-in: if this is on for a provider (and sign-up is open), a login from an unknown account creates a new account. It takes the provider's e-mail address, unless the provider marks it unverified. If that address is already in use, sign-in is refused: sign in to the existing account and link the provider in Settings instead.
  • Removing a provider also removes the links to it.

Linked accounts

Settings lists every configured provider with a Link or Unlink button. Linking sends you to the provider and back. The card is hidden when no provider is configured.

Access tokens

  • What: a personal token for scripts. It acts as you, on the JSON API only (not on the website).
  • Format: starts with dxf_. Send it as Authorization: Bearer dxf_....
  • Fields: a name (up to 64 characters) and an expiry: 30 days, 90 days (default), 1 year, or never.
  • Gotchas: the token is shown once, right after you create it, and only a hash is stored. The list shows the first characters, when it was created, last used and when it expires. Revoke a token to stop it working at once.
  • Changing the password revokes all your tokens. Tokens are created and revoked only on the website, not through the API.
curl -s -H "Authorization: Bearer $DEXAFIX_TOKEN" localhost:8080/api/v1/users/1/estimates

API authentication

Every API request except GET /healthz must be authenticated, with one of:

  • Authorization: Bearer <personal access token> (see above).
  • Authorization: Bearer <ID token> from an OpenID Connect or Sign in with Apple provider, for an account linked to that provider. It must be a JWT signed by the provider and issued for this application's client ID. Opaque access tokens are not accepted.
  • HTTP Basic with the e-mail address and password, while password sign-in is on: curl -u you@example.com:password .... Refused for an account with two-step verification on or required; such accounts use an access token.
  • The browser session cookie.

Responses are 401 when not authenticated and 403 when the role is not enough. A user can reach only their own /users/{id}/... routes; other ids answer 404.

Rate limiting

Failed password sign-ins are counted in memory: 10 per login name and 60 per client address in 15 minutes. After that sign-in answers 429. Successful sign-ins are never counted. Counters reset when the server restarts. Behind a reverse proxy set Trusted proxies on the Admin page, or everyone shares the proxy's address and its count. On a public deployment also limit sign-in attempts at the proxy. Form posts are capped at 1 MiB.

Gray values (calculated while typing)

While you fill in a form, an empty field shows a gray value when it can be calculated from what you typed. Weight, body fat %, fat mass and fat-free mass calculate from each other: any two give the rest. On the DEXA form, lean mass + bone mass gives fat-free mass. A typed value is never replaced. Gray values are saved with the form unless you type something else. This needs JavaScript; without it the fields stay empty.

Gotcha: a scan only calibrates the scale when the scale has a reading of the same kind on the same day. Add your scale readings for the scan day (Calibration). Deleting a scan removes its calibration.

Tick Athlete mode when the scale was set to its athlete setting (which changes how it estimates fat). The box starts out as your default from Settings. See Athlete mode for the effect.

Gotcha: the gray calculated values (see above) work on this form too. Deleting a reading cannot be undone.

Estimates

Page: /u/{id}/estimates (the page you land on after sign-in). It shows an overview of the latest values with a trend chart, the daily table, and the calibrations in use. The estimates are cached in memory per user and invalidated automatically when your data or settings change, so the page is fast but never stale.

How the daily estimates are computed

Each field is handled on its own. The estimated fields are weight, body fat, fat mass, fat-free mass, bone mass, lean mass, hydration, visceral fat index, BMI, FMI, LMI and the A/G ratio.

  1. Daily average. Readings are averaged per day, per field and per group (method plus athlete mode). Missing values are ignored.
  2. Most accurate reading. Each day uses the group whose method ranks highest for that field (Method accuracy). A method without a value for the field is skipped, so a caliper reading with only body fat does not hide the scale weight.
  3. Rolling average. Each day is averaged over the real readings within 3 days before and after it (a 7-day window, shorter at the ends). Only real readings count, never filled-in days. With at least 3 days with a real reading in the window, that average is the day's value; otherwise a day with a reading keeps it.
  4. Missing days get a value on a straight line between the nearest days that have one (origin interpolated). After the last such day the value is repeated up to today (origin held).
  5. Calibration. On each DEXA day, the offset (DEXA minus the scale's reading that day) is recorded. See Calibration.
  6. Estimate. A DEXA value is used as it is (origin dexa). Other days are corrected by the offset: before the first calibration with its offset, between two calibrations blended with a smooth curve, after the last calibration with the last offset.

Fat mass is calculated as weight x body fat % / 100 on every day with a weight, and fat-free mass as weight minus fat mass, so the two always add up to the weight. Lean mass is fat-free mass minus bone mass (only on days with both). BMI, FMI and LMI are weight, fat mass and lean mass divided by height squared; without a height in Settings they are left out. The A/G ratio is android fat % divided by gynoid fat %, from DEXA scans; after a scan the latest ratio is held until the next one.

Only body fat % and bone mass are corrected with an offset. Weight is never corrected, nor are hydration and visceral fat index.

Reading the table

  • A DEXA badge marks a value from a DEXA scan; a corr. badge marks a corrected value.
  • Faded values are interpolated or held. A gray est tag in front of a date marks a row with a value interpolated between two readings.
  • Hover a value to see its origin (measured, interpolated, held, dexa), the method and mode it is based on, and the raw reading.
  • The overview tiles show the latest value with the change; the chart has a selector for the measurement and the time range.

Method accuracy

  • What: a ranking of the measurement methods, most accurate first. Page: Settings.
  • Default: hydrostatic, BodPod, caliper, smart scale, tape, visual AI.
  • Effect: when several methods have a reading for the same field on a day, the highest-ranked wins.
  • How to change: drag the rows (or use the up and down buttons); without JavaScript there are rank number inputs. In the API: PUT /api/v1/users/{id}/settings with "method_ranking": ["bodpod", "scale"]; methods you leave out follow in default order.
  • Gotcha: a method only wins for fields it actually measured.

Athlete mode

  • What: many scales have an athlete setting that changes their estimate. A reading in athlete mode is a different kind of reading from a normal one.
  • Setting: Athlete mode by default in Settings. It presets the checkbox for new readings, is applied to API readings that leave athlete_mode out, and to Withings imports. Default: off.
  • Effect: each reading keeps its own flag. DEXA calibration is kept separately for normal and athlete readings. If the normal and athlete group of one method both have a value on a day, the one matching your default wins.
  • Gotcha: changing the default does not change stored readings.

Calibration

The offset is DEXA - the reading on the scan day, using the scale's own value that day, not the 7-day average. Every group (method and athlete mode) with a reading of that field on the scan day gets its own offset; several readings of one group on one day are averaged first. A group without a reading on the scan day gets no offset from that scan.

Example: a DEXA scan on 2026-03-01 says body fat 18.0 %, while the scale says 20.0 %. The offset is -2.0 percentage points, so on 2026-03-02 a scale reading of 20.0 % becomes an estimate of 18.0 %.

The Calibrations in use card on the estimates page lists each scan's offsets per method and mode. If it says none, add scale readings on the day of a DEXA scan.

Range and columns

  • Range: 30 days, 90 days (default), 1 year or all time. It applies to both the chart and the daily table. Query parameter range with the values 30, 90, 365 or all.
  • Columns: the Columns menu above the table shows and hides columns. The choice is remembered per account. Columns added later start out visible.

Per-day Withings re-import and Strength Level

With Withings connected, an ↻ button on each row re-imports that one day. It replaces that day's Withings data: adds its Withings readings (even when manual readings exist), updates changed ones, and removes stored Withings readings that Withings no longer returns. It never touches manual readings. With Strength Level enabled for you, a ⇪ button sends that day's weight and body fat to Strength Level (see Strength Level).

Integrations

Withings

Each user links their own Withings account. Imported measurements are stored as scale readings with the source withings and the athlete-mode default from Settings.

Setup (administrator)

  1. In the Withings developer dashboard create an application and register the callback URL, for example https://dexa.example.com/integrations/withings/callback.
  2. As an administrator, enter the client id and secret in the Withings application card on the Admin page. They are stored encrypted. The redirect URL defaults to this server's own callback address. Withings is configured only there; the old DEXAFIX_WITHINGS_* variables are ignored with a warning.

Connecting works only when client id, secret and redirect URL are all set.

Connecting and importing (user)

  1. On the Settings or Estimates page choose Connect Withings and grant access. Finish within 10 minutes.
  2. Choose Import from Withings. It fetches the whole history.

Imported: weight, fat ratio, fat mass, fat-free mass, muscle mass, hydration, bone mass and visceral fat. Measurements Withings marks as possibly belonging to someone else (a guest) are ignored. Days are calendar days in your time zone. How each day is handled:

Day hasWhat happens
No readingsImported.
Withings readings onlyChanged ones are updated, identical ones left alone, new ones added. Nothing is deleted.
Manual readingsNew Withings readings are skipped and the day is listed in the result. Earlier imports are refreshed.

A manual entry is a deliberate value; averaging it with a Withings reading of the same weigh-in would distort the day. To import such a day anyway use the per-day ↻ button (see above) or ?day= on the API. Disconnect Withings forgets your tokens; imported readings are kept.

Strength Level

Sends your estimated weight and body fat to your Strength Level account, so its strength standards use your real body weight.

  • Permission: an administrator must enable Strength Level sync for you on the Admin page (Strength Level permissions). Until then the card does not appear and the endpoints answer 403.
  • Login: your Strength Level e-mail and password, stored encrypted. Only e-mail and password accounts work, not Google, Apple or Facebook sign-in. The login is tested when you save it, so a wrong password is reported at once. The password is never shown again. Remove login deletes it.
  • Single day: the ⇪ button on a row of the Estimates page sends that day and replaces an entry that is already there.
  • Multi-day sync (needs the extra multi-day sync permission): choose Last N days (default 90, 1 to 3650). Days missing on Strength Level are added. With Also update days that already exist ticked, days that exist there with other values are overwritten too. Nothing is ever deleted. It runs in the background, one day at a time with a short pause, so long periods take a while; the progress shows on the page. Only one sync per user runs at a time.
  • What is sent: the daily estimate of weight and body fat, including interpolated and held days. Days without a weight estimate are left out.

Admin

Page: /admin, administrators only (menu under your name).

Server status
Version, Go version, database driver and schema version, whether encryption is on, counts of users, scans, readings, active sessions and access tokens, and whether Withings is configured.

Users

  • Add user: name, e-mail and password. Works even when sign-up is closed.
  • Make admin / Remove admin: the last administrator cannot be removed.
  • Set password: sets a new password for a user (8 to 72 bytes). The user is signed out everywhere and their access tokens are revoked.
  • Reset link: makes a one-time password reset link, valid for 24 hours and shown once here (see Password reset). E-mail it sends it instead, when e-mail is set up.
  • Remove two-step: turns off a user's two-step verification and deletes their recovery codes. Use it for a user who lost their device and their recovery codes.
  • Delete: deletes the user with all their data, immediately and without undo. You cannot delete yourself.
  • Strength Level permissions: Enable Strength Level sync lets that user store a Strength Level login and send single days. Once enabled, Allow multi-day sync additionally lets them run the background sync of many days.

Network and retention

  • Base URL: the public address, scheme and host only, such as https://dexa.example.com. Saving it is accepted only while you use that address.
  • Trusted proxies: addresses or ranges of your reverse proxies, as in Running behind a reverse proxy. Empty trusts nobody.
  • Accept the PROXY protocol from the trusted proxies: off by default; needs trusted proxies. See PROXY protocol.
  • Keep the audit log for (days): 365 by default; 0 keeps it forever.
  • Remind me to rotate the encryption key after (days): empty by default, which never reminds. See Rotating the key.

These take effect at once, without a restart, and are stored encrypted in the database. There are no flags or environment variables for them.

E-mail

SMTP server, port (587 by default), encryption (starttls by default, tls, or none only for a server on localhost), user name, password (stored encrypted, never shown again) and sender address. Send a test e-mail to me checks the settings. The e-mail is used for password reset links.

HTTPS, HTTP/2 and HTTP/3

An optional HTTPS listener on its own port, with an uploaded certificate or a generated self-signed one. The page shows the certificate names, expiry, SHA-256 fingerprint and any bind error. See HTTPS, HTTP/2 and HTTP/3.

Audit log

The latest events on the page. See Audit log.

Server configuration

Commands: dexa-fix serve runs the web app, dexa-fix db manages the database, dexa-fix user recovers accounts, dexa-fix settings recovers from server settings that locked you out, dexa-fix info prints information about the binary. Each flag has an environment variable. A flag on the command line overrides the variable.

Settings on the Admin page

Some settings are not flags. Running behind a reverse proxy

dexa-fix speaks plain HTTP. For HTTPS put a reverse proxy such as nginx, Caddy or Traefik in front, and bind dexa-fix to a private address so nobody can bypass the proxy: --listen 127.0.0.1:8080.

A proxy hides who the visitor is and whether they used HTTPS. It passes both on in X-Forwarded-For, X-Forwarded-Proto and X-Forwarded-Host. Anyone can send those headers, so dexa-fix only believes them on connections from the trusted proxies set on the Admin page; from everyone else they are ignored, and a warning is logged once.

  • Trusted proxies (Admin page, Network and retention): comma-separated addresses or CIDR ranges, for example 127.0.0.1,10.0.0.0/8. The keyword loopback stands for 127.0.0.0/8 and ::1; private adds the RFC 1918 ranges and fc00::/7. Empty trusts nobody.
  • Base URL (Admin page): the public address, scheme and host only (no path). Optional when the proxy forwards Host and X-Forwarded-Proto correctly; set it for a fixed address. Saving it is accepted only while you use that address, so a typo cannot lock you out.

What changes when the proxy is trusted:

  • Sign-in limits and the audit log use the visitor's address. Without it everyone shares the proxy's address.
  • Cookies are marked Secure and Strict-Transport-Security is sent, as soon as the visitor used HTTPS (as reported by the proxy) or the base URL is https.
  • Provider callback URLs are built from the base URL, or else from X-Forwarded-Proto and the host.
  • Form posts pass the same-origin check only if the browser's Origin matches the host it visited, so the proxy must pass the original host (as Host or X-Forwarded-Host), or you set the base URL.

The address is read from X-Forwarded-For from the right: every address that belongs to a trusted proxy is skipped and the first one after that is the visitor. Make sure the proxy appends to this header instead of passing along what the client sent. Without X-Forwarded-For, X-Real-IP is used.

# nginx
location / {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

# Caddy (forwards the headers by default)
dexa.example.com {
    reverse_proxy 127.0.0.1:8080
}

# Traefik (docker labels)
traefik.http.routers.dexa.rule=Host(`dexa.example.com`)
traefik.http.routers.dexa.tls=true
traefik.http.services.dexa.loadbalancer.server.port=8080

dexa-fix must be served from the root of its host. A sub-path such as example.com/dexa/ is not supported. In Docker the proxy reaches the app from the network's bridge address: trust that network's range, or private, and only ranges nothing but your proxies can send from. For Withings, the redirect URL on the Admin page has to be the public callback address.

PROXY protocol

The PROXY protocol (HAProxy versions 1 and 2) passes the visitor's address on the TCP connection itself, before any HTTP. Use it with a balancer that works at TCP level and adds no X-Forwarded-For. Turn on Accept the PROXY protocol from the trusted proxies on the Admin page; it needs trusted proxies.

  • A connection from a trusted proxy may start with the header, and the address in it becomes the visitor's address. The header is optional, so a balancer that does not send it cannot lock anyone out.
  • A connection from any other address may not start with the header. It is refused, so nobody can claim an address.
  • With the setting off, connections pass through untouched. It applies to the plain and the HTTPS listener, to each new connection at once.

The header does not say whether HTTPS was used, so set an https base URL for Secure cookies.

# haproxy.cfg: TLS ends at HAProxy, which sends the address with PROXY v2
frontend dexa
    mode http
    bind :443 ssl crt /etc/haproxy/dexa.pem
    http-request set-header X-Forwarded-Proto https
    default_backend dexa

backend dexa
    mode http
    server dexa 127.0.0.1:8080 send-proxy-v2

# nginx.conf, stream context: dexa-fix serves HTTPS on port 8443
stream {
    server {
        listen 443;
        proxy_pass 127.0.0.1:8443;
        proxy_protocol on;
    }
}

With an AWS Network Load Balancer, use a TCP listener on port 443 that forwards to a target group on port 8443 (dexa-fix serving HTTPS with a certificate you upload), and turn on Proxy protocol v2 for the target group. Trust the address range the load balancer connects from.

HTTPS, HTTP/2 and HTTP/3

dexa-fix can serve HTTPS itself. Behind a reverse proxy you usually leave this off. Plain HTTP stays on --listen (HTTP/1.1, and cleartext HTTP/2 for proxies that speak it). Set HTTPS on the Admin page, under HTTPS, HTTP/2 and HTTP/3:

  • Certificate: upload a PEM certificate chain and a PEM private key (stored encrypted; the key is never shown again; leave both empty to keep the saved one), or let dexa-fix generate a self-signed one: ECDSA P-256, valid 365 days, renewed automatically 30 days before expiry. Its names are the ones you give, or else the base URL's host plus localhost, 127.0.0.1 and ::1.
  • HTTPS port: 8443 by default, and it must differ from the plain port. HTTPS has its own listener, so a bad certificate or port cannot lock you out of the plain one. HTTP/2 and HTTP/1.1 are offered by ALPN, on TLS 1.2 and later.
  • Also serve HTTP/3 (QUIC): on the UDP port with the same number as the HTTPS port, advertised with an Alt-Svc header. The UDP port must be reachable.

The Admin page shows the certificate names, expiry, SHA-256 fingerprint and any bind error. With Docker, publish both ports: -p 8443:8443 -p 8443:8443/udp.

Browsers and apps trust a self-signed certificate only once you add it, and browsers use HTTP/3 only with a trusted certificate. There is no HTTP to HTTPS redirect yet.

Database

SQLite (default) or Postgres, through one query path. Schema changes are versioned migrations, embedded per backend.

  • SQLite: default DSN file:dexa-fix.db. Connections always enforce foreign keys and wait up to 5 seconds for locks, and file databases run in WAL mode, so the DSN needs no pragmas. The database file is created with mode 0600, and a warning is logged if an existing file is readable by group or others. WAL mode also creates -wal and -shm files next to the database; back up all of them together, or use a SQLite-aware backup.
  • Postgres: supported version 18. Use --db-driver postgres and a DSN like postgres://user:pass@host/dexafix, given through DEXAFIX_DSN or --dsn-file.
  • Migrations: serve applies pending migrations at startup unless --auto-migrate=false. It refuses to start if the database schema is newer than the binary, so upgrade dexa-fix first. Databases created by pre-1.0 builds carry a higher schema version and are refused; start from a fresh database.

Moving from SQLite to Postgres

export DEXAFIX_TO_DSN='postgres://user:secret@localhost/dexafix'
dexa-fix db copy --from-driver sqlite --from-dsn file:dexa-fix.db --to-driver postgres
dexa-fix serve --db-driver postgres --dsn-file /run/secrets/dexafix-dsn

The target is migrated to the latest schema first and must be empty. Ids are kept and Postgres sequences are reset. The copy is a single transaction, so a failure leaves the target untouched. The source is not changed but must already be fully migrated (db migrate up). Encrypted values are copied unchanged: the server on the target needs the same encryption key, or run db rekey on the target with the source key as a previous key (see Encryption).

Encryption

These values are encrypted with AES-256-GCM before they are stored: each user's Withings tokens, the Strength Level login, sign-in provider secrets (including the Apple key), the Withings application credentials and other server settings, e-mail addresses, and each user's two-step verification secret. Each value is tied to its row, so copying it to another row makes it unreadable. Each e-mail address also gets a keyed hash so addresses can be searched and kept unique without decrypting them. Passwords, access tokens and recovery codes are stored only as hashes.

Names, measurements and height are not encrypted by the application. Use disk or database encryption for those.

The key comes from, in this order:

  1. The environment variable DEXAFIX_ENCRYPTION_KEY: 32 bytes as 64 hexadecimal characters or as base64. There is no command-line flag, because command lines are visible to other processes.
  2. The key file (--encryption-key-file or DEXAFIX_ENCRYPTION_KEY_FILE, default dexa-fix.key in the working directory). If neither exists, dexa-fix creates the file with a new random key and mode 0600 and logs a warning, but only for a new database or one without encrypted values. If the database already holds encrypted values, a missing key file is an error and nothing is created, so a key file that did not mount is reported instead of replaced.
  • In containers, put the key file on a persistent volume or set the variable.
  • Back up the key separately from the database. Without it the encrypted values cannot be read and the server does not start. Keeping the key next to the database backup defeats the purpose.
  • The database remembers which key it belongs to (a check value in the crypto.check setting that reveals nothing about the key). Starting with a different key fails with a message that says so.
  • For SQLite, serve logs a warning when the key file is in the same directory as the database file, as with the container image defaults. A leak of that directory exposes both the encrypted values and the key. Prefer DEXAFIX_ENCRYPTION_KEY from a secret store, or a key file on a separate secret mount.
  • Values stored before encryption was on are encrypted automatically at startup.

Rotating the key

Stored values look like enc:v2:<key id>:<data>; the key id is the first eight hex characters of the SHA-256 of the key. Older enc:v1: values stay readable.

  1. Stop the server and back up the database and the key file.
  2. Generate a new key, for example openssl rand -hex 32.
  3. Make it the current key and give the old one as a previous key: DEXAFIX_ENCRYPTION_KEY=<new> and DEXAFIX_ENCRYPTION_KEY_PREVIOUS=<old>, or a new key file plus --encryption-key-previous-file.
  4. Run dexa-fix db rekey --dry-run. It reports how many values would change and fails if any value cannot be opened.
  5. Run dexa-fix db rekey. In one transaction it re-encrypts e-mail addresses, integrations, server settings (including the cookie key), provider secrets and two-step verification secrets, recomputes the e-mail lookup hashes and stores the new check value. It prints a count for each kind, such as two-step secrets re-encrypted: 2. It either completes or changes nothing, and can be repeated.
  6. Start the server with only the new key. The cookie key does not change, so sessions stay valid.

Between steps 3 and 5 the server still starts: it reads old values with the previous key, writes with the current one, and logs a warning until db rekey has run. Run db rekey with the server stopped.

Rotation is manual on purpose: the key belongs to the operator, db rekey is offline, and the AES-GCM usage limits are far out of reach. Rotate when the key may have leaked, when someone with access leaves, or when your policy asks for it. The Admin page shows the key id and since when it has been in use (at least). Set Remind me to rotate the encryption key after (days) on the Admin page to get a reminder there when the key is older than that; empty gives none. The page also says when db rekey is due after a key change.

Data export and GDPR

Under Settings → Your data every user can download two JSON files. They serve a person's right of access and data portability (GDPR articles 15 and 20).

  • Settings and personal details: name, e-mail, role, height, settings, permissions, sign-in methods (provider and account id), passkey names and dates (never the keys), access token names and prefixes, whether two-step verification is on (two_factor.enabled; never the secret or recovery codes), whether Withings and Strength Level are connected (and the Strength Level e-mail address), and the audit events about the account.
  • DEXA scans and scale readings: everything the user measured, including notes.

Credentials are never included: the files say whether a password, token or integration exists, not what it is. The same files are available to scripts at GET /api/v1/users/{id}/export/profile and /export/data. Every export is recorded in the audit log. Erasure: an administrator deleting a user (Admin page) removes all their measurements and settings, clears the IP addresses in the events about them, and the events no longer refer to them.

Audit log and retention

Security-relevant events are recorded in the database: sign-ins (successful, failed and blocked), sign-outs, account creation, profile, password, token, sign-in method and two-step verification changes, imports, integration connects, data deletions, exports, and every administrator action (users, roles, permissions, providers, server settings). Each event has a time, who did it, whom it concerned, a short detail and the client's IP address. Details never hold passwords, tokens, e-mail addresses or login names.

  • Who sees it: administrators see the latest 100 events on the Admin page and the whole log at GET /api/v1/audit. Everyone sees the latest events about their own account in Settings (Recent account activity) and at GET /api/v1/users/{id}/audit.
  • Retention: events are deleted after the Keep the audit log for (days) setting on the Admin page (default 365; 0 keeps them forever). The purge runs at startup and then every few hours.
  • Noise: failed and blocked sign-ins are recorded at most once per client address and minute, with a count of the ones left out, so a flood cannot fill the database.
  • Recording an event never fails the request that caused it; a failed write is logged.
  • API: limit, before_id and, for administrators, user_id query parameters.

Pagination and filters

List endpoints (dexa-scans, scale-readings) take:

  • limit: page size. Default 1000, maximum 10000.
  • before: cursor from the previous page.
  • since, until: only items in that time range. RFC 3339 (2026-03-01T00:00:00Z) or YYYY-MM-DD.

The response header X-Next-Cursor holds the cursor for the next page. It is absent on the last page. Pass it unchanged as before.

curl -si -H "Authorization: Bearer $DEXAFIX_TOKEN" \
  'localhost:8080/api/v1/users/1/scale-readings?limit=500&since=2026-01-01'
# ... X-Next-Cursor: 1767254400000000000.42
curl -s -H "Authorization: Bearer $DEXAFIX_TOKEN" \
  'localhost:8080/api/v1/users/1/scale-readings?limit=500&since=2026-01-01&before=1767254400000000000.42'

The audit endpoints use limit, before_id and (administrators) user_id.

Security notes and limitations

  • Encryption is partial. Measurements, height and names are not encrypted by the application. Protect the database file or Postgres database and its backups with disk or database encryption. Losing the encryption key makes the encrypted values unreadable. See Encryption.
  • Rate limiting is in memory and basic. It covers failed password sign-ins only and resets on restart. Add limits at the proxy on a public deployment.
  • Secrets stay off command lines. Use environment variables or *-file flags for the Withings secret, database passwords and the encryption key.
  • Browser hardening. A strict Content-Security-Policy (scripts from the app itself only), X-Frame-Options: DENY, same-origin checks on form posts, and no-store caching for pages.
  • Behind a proxy the proxy should enforce HTTPS, and the Withings redirect URL on the Admin page must be the public URL. Only trust proxy ranges that nothing else can send from.
  • The database file is created with mode 0600; a warning is logged if an existing one is group or world readable. Keep the key file at 0600 as well.
  • Tokens are shown once and stored hashed; revoke any you no longer use. Prefer expiring tokens.
  • HTTPS certificates. A self-signed certificate is trusted by nobody until you add it, and browsers use HTTP/3 only with a trusted certificate. The private key is stored encrypted. There is no HTTP to HTTPS redirect yet.
  • Password reset links are bearer credentials: whoever reads the mailbox, or the link, can set a new password. Use STARTTLS or TLS for the SMTP server.
  • This is a measurement tool, not a medical device. Estimates correct a scale by a DEXA offset and say nothing about health.
